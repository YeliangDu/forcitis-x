# HWK 全功能现代化：目标驱动实施计划

## 最终目标

用户可以用新应用完成目标版本旧应用的相同工作，并得到一致结果。范围包括所有计算体系、材料和截面选择、荷载组合、有限元、绘图、验算、计算书，以及原工程无损打开、编辑、保存、重开和原版兼容验证。界面窗口、菜单、属性、工程树、快捷键和操作流程逐项对照。先恢复旧行为；现代技术不得改变默认值或擅自修正旧算法。

## 组织方法

采用Goal-Driven的明确Goal、可验证Criteria、主代理独立验收、执行代理持续迭代。首次启用一个主代理和一个执行代理。用户2026-10-18已授权风险可验证可回收的并行，现允许主线旁增加一张隔离取证卡；具体冻结输入、独立验收、原子导入和回收规则见AGENTS.md与planning/parallel-cards.json。共享文件保持单一写入者。实现代理每轮选一个可验收的真实业务切片，提交代码、证据、检查结果和剩余缺口。主代理重跑检查、核对原版来源，决定通过、继续或转入补证据。

每轮：读状态→选依赖已满足的任务→规定验收案例→获取原版基线→实现→差分→独立验收→更新台账和交接。约5分钟检查活动是观察策略，不是强制重启时限；长计算保留进程标识与日志。连续两轮无新证据时改变调查方法，仍不可推进时登记阻塞、转做独立任务，避免无效循环。

原版行为获取失败、授权/环境缺失、版本不明时，目标保持未完成。按实际平台支持使用持续执行；上下文交接、用户停止、预算或环境限制优先于模板中的无限运行措辞。项目完成仅由最终Criteria决定，仓库准备完成不等于产品完成。

## 阶段与完成条件

### B：建立可信基线和范围（先做）

B01 检查包内MSI/CAB和PE版本、哈希、组件和依赖；在工作副本解包。输出版本来源、文件库存，澄清标签与资源版本关系。先只读检查，运行安装器前记录可用Windows环境与授权；使用实际可用环境，外部付费资源或远程变更另行取得授权。

B02 建立可重复的Windows原版运行环境，登记系统、运行库、区域设置、字体、数据库、规范配置、授权状态；运行样例并导出报告、图形和保存重开结果。原版工作副本与黄金输出隔离，锁定环境和所有输入哈希。

B03 枚举全部菜单、计算体系、对象类型、属性、材料/截面、规范选项、异常、报告类型、文件版本及绘图操作。静态库存与原版UI及可用示例交叉核验，记录无法访问项；主代理审核后才能将 `scope.inventory_complete` 设为true。不得以“已发现的子集”冒充全量。

B04 按库存建立验收案例与需求追踪。高风险有限元、规范分支、材料查表、隐藏全局状态、数值边界优先取证。每个体系至少一条真实工程全链，再补边界/组合/失败案例；固定样例与未用于调试的保留案例分别管理。

### P：门窗样例1完整闭环

P01 从安装包真实样例打开工程，恢复对象关系和输入绑定；建立编辑、原版重算、导出与保存的可复现步骤。

P02 沿最终报告结果反追输入、查表、默认值、规范、全局状态、原生函数及执行顺序；按业务链恢复荷载、玻璃、杆件有限元、连接及其他启用计算。一次只修复一个有证据的差异，不以独立函数数量计完成率。

P03 绘图与计算书逐项对照：数值、单位、精度、文本、章节条件、合格/不合格、分页、图形尺寸和标注。工程编辑保存后在新应用和原版重开，核对对象、属性、引用、数据库关联和重算结果；未知字段保留策略要有实测证据。

P04 独立复跑原样例、参数变体和保留案例。任一主链仍依赖fixture、常量替代或原DLL计算，即不满足独立完整替代。试点验收后更新成本估算与架构决定。

### E：扩展所有计算体系

按B03实际库存逐项推进，其顺序由真实使用、风险及共享依赖决定；玻璃、石材、金属及其他体系名称均以包与运行库存为准。每新增一项同时补输入、计算、图形、报告、文件往返及失败测试，回归已有体系。建立规范×材料×边界条件×文件版本覆盖清单，组合测试不能替代关键规范分支的显式验收。

### R：全量替代验收

主代理核查无漏项库存、需求到案例到实现到证据的追踪；复跑全部真实工程、边界、失败及保留案例。完整安装/卸载、桌面操作、打印导出和性能对照也须通过。由使用者完成代表性业务操作验收；需要工程专业判断的差异由专业人员裁定并记录，代理不自行降低安全相关判定标准。

## 对照与判定规则

原版环境与程序以哈希锁定。输出包含数值与中间量、实际激活分支、报告文本/图形、对象及文件语义。默认离散值、状态、文本与文件语义一致；连续数值先追求相同运算顺序和精度。确需容差时，按变量、单位、原版显示精度与工程意义登记依据，经主代理审核；验算结论与阈值边界不得因容差掩盖翻转。不可统一设置宽松百分比。

不能以字节完全相同取代语义验证，也不能以语义相同掩盖无法被原版打开。截图证明界面观测，静态反汇编证明局部指令，合成测试证明给定输入；各自不自动证明端到端等价。

每条功能记录包含ID、体系、入口、原版版本、输入哈希、案例、预期输出、比较规则、代码位置、证据目录、状态及差异。`planning/acceptance.json` 是发布检查入口；先审核完整性，再判断条目，缺失即失败。

## 产物与检查

- 原资产：`vendor/`；清单：`evidence/baseline/`。
- 自动化、采集和比较器：`scripts/`；实现：`replica/`。
- 单例证据：`evidence/acceptance/<功能ID>/<案例ID>/`，包含原版/新版原始输出、输入、环境、命令、差分和验收结论。
- 任务依赖：`planning/tasks.json`；范围：`planning/scope.json`；最终门槛：`planning/acceptance.json`。
- 当前bootstrap检查器只校验台账门槛、路径及基本记录，不证明证据真实性或数值一致。业务比较器建立后由主代理运行并审查；禁止将台账检查通过等同业务验收。

## Goal → 阶段 → 工作包 → 卡 → 证据

整体Goal、各阶段成果、交付物/排除项/阻塞条件及工作包定义以 `planning/stage-contracts.json` 为可执行合同；当前独立验收状态以 `planning/stage-progress.json` 为准。原全量替代范围与上文业务标准不变。卡片只是工作包的一次执行尝试，不能用已结束卡片数表示工作完成。

每个工作包有稳定ID、明确goal、输入、预期输出、done_when、依赖、责任与阻塞处理。调度器派下一执行卡前先由独立只读goal-assessor核对WBS对HWK-G001的覆盖和可组合性；合同或范围变化须重新审查。调度器只派当前阶段依赖满足的叶子包；阶段所有工作包独立通过仅产生候选，另起新会话分别审查阶段实际达成与对整体Goal的贡献，全部放行条件满足后才推进。计划放行不等于阶段或总Goal完成，否定判断保留并暂停。独立审查绑定合同、范围、支持文件及真实检查日志哈希；R01仍须所有义务、前阶段独立判断及原业务门槛通过。工作包复盘上限触发暂停/重新规划，不构成放弃目标或降低标准的理由。合同与进度由外部控制器维护；执行代理不可直接改目标/额度，独立验收以明确包目标回报PASS/PARTIAL/BLOCKED。

P02计算实施和E01逐体系实施须先基于真实库存分解；未发现体系不凭空列数，也不把“实现全部计算体系”作为可直接派卡的大包。规划包审核后的子包覆盖全部冻结功能ID且无依赖环，控制器才注册。新线索先进入分解建议，不自动开卡。
